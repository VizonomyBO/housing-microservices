# Epic 1: Shared Data Layer & Persistence

**Context**: `packages/shared_data_layer` is the canonical source for schema, migrations, repositories, DTOs, and maintenance workflows that back every service. The current implementation already includes conversations, telemetry, knowledge graph, workflow helpers, and maintenance routines described across `docs/data/schema_and_persistence.md` §§3.2–3.10, `docs/data/knowledge_graph.md`, and `docs/overview/monorepo_structure.md`.

**Key Design Docs**
- `docs/data/schema_and_persistence.md` (tables, constraints, workflows)
- `docs/data/knowledge_graph.md` (graph + workflow semantics)
- `docs/overview/monorepo_structure.md` (package layout, CLI expectations)
- `docs/agents/implementation.md` §4 (state + repository usage)

> **Identity note:** The shared layer never owns a `users` table. Identity is provided by upstream services; all tables store `owner_user_id` as a raw UUID and enforce integrity through constraints and repository validation.

## Task 1.1 — Align Schema & Identity Boundaries

**Goal**: Ensure the migration (`000000000001_initial.py`) and ORM models cover every table listed in §§3.2–3.4 (documents, ingestion_jobs, artifacts, conversation_documents) plus the base-document helpers (`base_documents_by_country`) and GC tracking tables (`document_gc_events`).

**What to do**
- Keep the single-file migration updated with new columns/enums. LTREE + pgvector support must remain in-repo.
- Encode hash-based deduplication, ref-counted deletion, ISO country validation, and base-doc partitions with explicit constraints.
- Document the expectation that `owner_user_id` references external identity and that there is **no** FK to a local users table.

**Deliverables**
- Schema + ORM definitions that match the constraints in `schema_and_persistence.md`.
- Narrative updates describing how base documents are attached/auto-managed.

## Task 1.2 — Conversations, Messages, Telemetry & Pillar Answers

**Goal**: Bring conversation/message persistence (§3.6) and retrieval telemetry (§§3.5–3.7) into parity with implementation.

**What to do**
- Describe and maintain: `conversations`, `messages`, `message_tool_calls`, `message_citations`, `agent_state_checkpoints`.
- Capture async analytics tables: `retrieval_runs`, `retrieval_run_items`, `pillar_answers`, `pillar_answer_sources`.
- Explain how repositories expose deterministic replays for LangGraph checkpoints and how pillar answers feed `/v1/pillars/{country_code}`.

**Deliverables**
- Updated epic narrative plus tasks covering CRUD, DTOs, repository helpers, and validation (visibility overrides, attachment guards).
- Explicit testing requirement for factories + Testcontainers around these tables.

## Task 1.3 — Retrieval, Graph, and Workflow Materializations

**Goal**: Keep retrieval (`chunks`, `chunk_metrics`, `active_chunks` view), graph (`graph_entities`, `graph_edges`, `graph_evidence`, `graph_communities`, `graph_edge_evidence_rollup`, `graph_hot_entities`), and workflow (`workflow_graphs`, `workflow_nodes`, `workflow_edges`, `workflow_versions`, `workflow_version_diffs`) assets aligned with `docs/data/knowledge_graph.md`.

**What to do**
- Document chunk partitioning, pgvector index strategies, table normalization payloads, and telemetry hooks.
- Capture the LangGraph-supporting helpers (workflow refresh functions, graph entity rollups, maintenance CLI commands).
- Reference the procedural helpers in `shared_data_layer/db/events.py`, `maintenance.py`, and `procedures.py`.

**Deliverables**
- Tasks for building/refreshing materialized views, LTREE stored procedures, and orchestration helpers.
- Tests that ensure refresh helpers run only when relevant base tables mutate.

## Task 1.4 — Maintenance Workflow & CLI Tooling

**Goal**: Describe the operational automation already implemented: `document_gc_events`, garbage-collection CLI, workflow refresh helpers, base-document auto-attach, `active_chunks` refreshes, and graph/workflow maintenance jobs.

**What to do**
- Detail the CLI entry points (e.g., `shared-data-layer migrate`, `shared-data-layer maintenance refresh-active-chunks`, GC commands).
- Capture policies for `document_gc_events`, base doc validators, and maintenance telemetry exports.
- Document the expectation that repositories call helpers instead of issuing ad-hoc SQL for refreshes/maintenance.

**Deliverables**
- Epic tasks that cover writing/maintaining maintenance commands, hooking them into CI/CD, and adding regression tests.

## Task 1.5 — Repositories, DTOs, Factories & Test Harness

**Goal**: Codify the repository patterns, Pydantic DTOs, Polyfactory builders, and Testcontainers-powered tests already living in the package.

**What to do**
- Keep repositories (`documents`, `retrieval`, `knowledge_graph`, `workflows`, `conversations`) aligned with the DTOs described in the design docs and ensure eager loading avoids `MissingGreenlet`.
- Require deterministic Polyfactory builders, shared fixtures, and end-to-end ingestion tests (with `--end-to-end`) to validate new schema changes.
- Document tooling expectations: `uv sync`, `ruff`, `pyright/ty`, `pytest -n auto`, and the no-Docker-manual-start rule.

**Deliverables**
- Updated task list and acceptance criteria describing DTO coverage, repository unit tests, and end-to-end smoke tests.
- Linkbacks to `docs/overview/monorepo_structure.md` and `docs/agents/implementation.md` to keep consumers aligned.

# Epic 7: Authentication Email Service

**Context**: Epic 7 covers all authentication-related email functionality: email verification (confirm registration), password recovery (forgot password), and password change notifications. This epic requires Terraform infrastructure for AWS SES in the `ArchaaS/` folder and integration work in `services/auth-service/`. The existing auth service has basic endpoints for forgot/reset password and change password, but lacks actual email delivery. The registration flow creates users with `status="pending"` and `email_verified=False` but has no verification mechanism. Every email operation must respect rate limits, never reveal account existence, and maintain audit trails for compliance.

  - `ses_domain` — domain for SES identity
  - `email_verification_url_base` — frontend URL for email verification links
  - `password_reset_url_base` — frontend URL for password reset links
- Add outputs for SES identity ARN and configuration set name.

**Deliverables**

- Updated `ArchaaS/variables.tf` with SES variables.

## Task 7.2 — SES Email Templates

**Goal**: Create versioned, branded email templates for all authentication email flows that can be managed via Terraform.

**What to do**
- Define `aws_ses_template` resources in `ArchaaS/ses.tf` for:
  - **Email Verification** (`email-verification`):
    - Subject: "Verify your email address"
    - Body: Welcome message, verification link with token, expiration notice (24 hours), what happens if not verified
    - Template variables: `{{name}}`, `{{verification_link}}`, `{{expiration_hours}}`, `{{support_email}}`
  - **Password Reset Request** (`password-reset-request`):
    - Subject: "Reset your password"
    - Body: Reset link with token, expiration notice (1 hour), security warning if not requested
    - Template variables: `{{name}}`, `{{reset_link}}`, `{{expiration_minutes}}`, `{{support_email}}`
  - **Password Reset Confirmation** (`password-reset-confirmation`):
    - Subject: "Your password has been reset"
    - Body: Confirmation that password was reset via forgot-password flow, timestamp, contact support if unauthorized
    - Template variables: `{{name}}`, `{{timestamp}}`, `{{support_email}}`
  - **Password Changed Notification** (`password-changed-notification`):
    - Subject: "Your password was changed"
    - Body: Security notification for authenticated password change, timestamp, IP address hint, contact support if not you
    - Template variables: `{{name}}`, `{{timestamp}}`, `{{ip_address}}`, `{{support_email}}`
- Use HTML templates with inline CSS for email client compatibility.
- Include plain-text alternatives for accessibility.
- Parameterize frontend URLs so they can differ per environment (dev/staging/prod).

**Deliverables**
- Four `aws_ses_template` resources in Terraform with HTML and text bodies.
- Template variable documentation in code comments.
- Example of how to update templates without downtime (versioning strategy).

## Task 7.4 — Email Verification Flow (Confirm Registration)

**Goal**: Implement complete email verification flow so users can confirm their registration and activate their accounts.

**What to do**
- **Update User model** (`services/auth-service/app/models/user.py`):
  - Add `verification_token` column (VARCHAR 64, nullable, indexed)
  - Add `verification_token_expires` column (TIMESTAMP, nullable)
  - Verify `email_verified` and `status` columns exist (they do)
- **Create database migration** for new columns
- **Update UserService** (`services/auth-service/app/services/user_service.py`):
  - Add `set_verification_token(session, user, token, expires_at)` method
  - Add `clear_verification_token(session, user)` method
  - Add `verify_email(session, user)` method that sets `email_verified=True` and `status="active"`
- **Update `/register` endpoint** (`services/auth-service/app/api/auth.py`):
  - After creating user, generate verification token (use `generate_reset_token()` or similar)
  - Set token expiration to 24 hours
  - Call `email_service.send_verification_email()`
  - Update response message to indicate verification email sent
- **Create new endpoint `POST /v1/auth/verify-email`**:
  - Request body: `{ "token": "..." }`
  - Validate token exists and not expired
  - Call `UserService.verify_email()` to activate account
  - Clear verification token after use
  - Return success message
  - Rate limit: 10 per hour per IP
- **Create new endpoint `POST /v1/auth/resend-verification`**:
  - Request body: `{ "email": "..." }`
  - Find user by email, check if already verified
  - If not verified, generate new token and send email
  - Always return same response (don't reveal if email exists)
  - Rate limit: 3 per hour per IP

**Deliverables**
- Updated User model with verification token columns.
- Database migration for new columns.
- Updated `/register` endpoint with email sending.
- New `/verify-email` and `/resend-verification` endpoints.
- Unit tests for verification flow.

## Task 7.7 — Rate Limiting and Abuse Prevention

**Goal**: Enhance rate limiting to prevent email bombing and abuse across all email operations while maintaining security.

**What to do**
- **Per-email cooldown tracking**:
  - Create `services/auth-service/app/models/email_attempt.py`:
    - Model: `EmailAttempt(id, email_hash, attempt_type, attempted_at, ip_address)`
    - `attempt_type` enum: `verification`, `password_reset`, `resend_verification`
    - Store SHA-256 hash of email (not plaintext) for privacy
  - Add migration for `email_attempts` table
- **Cooldown logic**:
  - Before sending any email, check if email_hash has recent attempt of same type
  - Verification emails: 5-minute cooldown
  - Password reset emails: 5-minute cooldown
  - If cooldown active, still return success message (don't reveal)
  - Log the blocked attempt for monitoring
- **Exponential backoff for password reset**:
  - Track attempt count per email_hash in rolling 24-hour window
  - 1st attempt: immediate
  - 2nd attempt: 5-minute cooldown
  - 3rd+ attempts: 15-minute cooldown
  - After 5 attempts in 24 hours, block for 1 hour
- **IP-based rate limiting** (existing + enhancements):
  - `/forgot-password`: 3 per hour (existing)
  - `/resend-verification`: 3 per hour
  - `/verify-email`: 10 per hour
  - Add secondary limit: max 10 different emails per IP per hour across all endpoints
- **Suspicious pattern detection**:
  - Log when same IP requests emails for multiple different addresses
  - Log when same email_hash receives multiple attempts
  - Do NOT alert user or change response (timing attack prevention)

**Deliverables**
- New `EmailAttempt` model and migration.
- Enhanced rate limiting logic across all email endpoints.
- Monitoring/alerting hooks for suspicious patterns.
- Documentation of rate limit tiers and abuse response procedures.

## Task 7.8 — Security Measures and Audit Logging

**Goal**: Ensure all authentication email flows meet security best practices and compliance requirements.

**What to do**
- **Account existence protection** (verify across all endpoints):
  - Confirm `/forgot-password` returns identical response/timing for existing and non-existing accounts (already implemented)
  - Confirm `/resend-verification` returns identical response/timing
  - Add constant-time comparison for email lookups where applicable
- **Token security**:
  - Verification tokens: cryptographically random, 24-hour expiration, one-time use
  - Reset tokens: cryptographically random, 1-hour expiration, one-time use (already implemented)
  - All tokens cleared after successful use
  - Invalidate all active sessions after password reset/change (already implemented)
- **Audit logging**:
  - Log all email operations (type, timestamp, success/failure, user_id if found)
  - Do NOT log email addresses in plaintext (use user_id or hashed email)
  - Log successful verifications and password changes with user_id
  - Log failed attempts (invalid/expired tokens) without revealing which email
  - Ensure logs are structured JSON for observability stack
- **Email content security**:
  - All links must use HTTPS
  - Links include token only, not email (prevent enumeration)
  - Add security notice: "If you didn't request this, ignore this email"
  - Include timestamp in all emails for user awareness
- **Database security**:
  - Index `verification_token` and `reset_token` columns for fast lookups
  - Consider storing token hashes instead of plaintext tokens (optional enhancement)

**Deliverables**
- Security review checklist for all authentication email flows.
- Audit log format specification.
- Updated logging in all auth endpoints with structured format.
- Documentation of token lifecycle and security properties.

### SES Sandbox Mode

AWS SES starts in sandbox mode. To send emails:
1. Verify sender email address
2. Verify recipient email addresses (sandbox only)
3. Request production access for sending to any recipient

Document the production access request process in Terraform comments.
